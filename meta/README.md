# `meta/` — vendored Hyprland metadata

This directory holds the **upstream source of truth** that `hyprconf-core`'s
schema is derived from and checked against. Nothing here is edited by hand.

## Files

| File                       | Source                                                  | Purpose                                                                 |
| -------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------- |
| `hl.meta.lua`              | `/usr/share/hypr/stubs/hl.meta.lua`                     | The official autogenerated Lua API stub shipped by Hyprland.            |
| `hyprland-config-keys.txt` | Extracted from `hl.meta.lua` (`---@alias HL.ConfigKey`) | The authoritative, flat list of every configuration option key.         |
| `hyprland-descriptions.json` | `hyprctl descriptions -j` (0.56.2), `current` values stripped | Every option's description, default, `min`/`max` and value map, from the compositor itself. |
| `gen_sliders.py`           | —                                                       | Re-vendors the descriptions and regenerates `crates/hyprconf-core/src/schema/sliders.rs`. |

### Provenance

- Hyprland **0.56.1** (`v0.56.1`, commit `5c9377c1…`, built 2026-07-27),
  as reported by `hyprctl version` on the build host.
- `hl.meta.lua` header: _"This file is autogenerated. Do not edit by hand.
  Generator: scripts/generateLuaStubs.py"_.
- `hyprland-config-keys.txt` is the 353-entry `HL.ConfigKey` union from that
  stub, one `section.key` per line (dotted form; e.g. `decoration.blur.size`,
  `general.col.active_border`).

## How the schema maps to these keys

`hyprconf-core` stores option paths in **hyprlang `conf` notation**, where
sub-sections are separated by `:` and dotted key names (like `col.active_border`)
keep their `.`:

| `conf` path (schema)            | stub key (`hl.meta.lua`)        |
| ------------------------------- | ------------------------------- |
| `decoration:rounding`           | `decoration.rounding`           |
| `decoration:blur:size`          | `decoration.blur.size`          |
| `general:col.active_border`     | `general.col.active_border`     |
| `group:groupbar:col.active`     | `group.groupbar.col.active`     |
| `input:touchpad:natural_scroll` | `input.touchpad.natural_scroll` |

The mapping is mechanical: **replace every `:` with `.`**. The unit test
`schema::tests::every_option_path_exists_in_vendored_stub` performs exactly this
transform for every `OptionSpec` in the schema and asserts membership in
`hyprland-config-keys.txt`, so the schema can never reference an option that the
shipped Hyprland does not know about.

## Regenerating after a Hyprland upgrade

```sh
# 1. Refresh the vendored stub.
cp /usr/share/hypr/stubs/hl.meta.lua meta/hl.meta.lua

# 2. Re-extract the flat key list (drops the trailing blank line).
sed -n '/^---@alias HL.ConfigKey/,/^[^-]/p' meta/hl.meta.lua \
  | sed -n 's/^---| "\(.*\)"$/\1/p' \
  | grep '\.' > meta/hyprland-config-keys.txt

# 3. Refresh the option descriptions (and the slider hints derived from them)
#    from the running compositor.
hyprctl descriptions -j | python3 meta/gen_sliders.py --vendor   # = just refresh-descriptions

# 4. Run the tests; coverage gaps, stale keys, changed value maps and changed
#    defaults all surface as failures.
just test
```

### What the descriptions are used for

- **Coverage:** `schema::tests::schema_covers_every_option_the_compositor_describes`
  fails if Hyprland describes an option the schema lacks (or the reverse).
- **Value maps:** an option with a `map` (`0 = disabled, 1 = …`) must be a
  dropdown over exactly those values.
- **Defaults:** schema defaults must equal Hyprland's (a handful of "unset"
  sentinels with no typed equivalent are listed in the test).
- **Slider hints:** `min`/`max` become the UI slider span. They are *not*
  validation limits — Hyprland accepts and keeps values beyond them (checked
  with `--verify-config` and on a live session), so hyprconf does too.

Paths in the descriptions use the `.conf` spelling (`tap-to-click`,
`input-capture`); the schema keys options by the stub spelling and maps
between the two with `schema::canonical_path` / `schema::conf_path`.

## Verifying against the compositor

The stub tells you which option *keys* exist. It does **not** tell you the shapes
the `hl` API accepts at runtime — and Hyprland is strict about those, rejecting
unknown table fields and wrong argument forms at load. Worse, some mistakes load
*successfully* and do nothing (a window rule whose rule text ended up in `name`).

The authority for shapes is the binary itself:

```sh
Hyprland --verify-config -c /path/to/config.lua
```

Its error messages are self-documenting (`hl.window.tag: expected a table
{ tag, window? }`), which is how the tables in
`crates/hyprconf-core/src/lua/{dispatch,rules}.rs` were derived. The shipped
example config at `/usr/share/hypr/hyprland.lua` is the other reference.

`crates/hyprconf-core/tests/hyprland_verify.rs` automates this: it converts
fixtures and asserts the real binary accepts the output, skipping when no
Hyprland is installed.

> **Note:** `--verify-config` executes top-level side effects — a bare
> `hl.exec_cmd("waybar")` really does launch waybar. `hyprconf_core::verify`
> comments those out in the temporary copy it checks.

## What is still encoded by hand

Value **types** (bool / int / enum / gradient / gap …), human **labels** and
**variant explanations** live in `crates/hyprconf-core/src/schema/data.rs`.
The descriptions file pins *what exists*, the *value maps* and the *defaults*
(tests fail on drift), but it does not carry types precisely enough to
generate them: it reports `1` for a float like `active_opacity`, and colours,
gradients and gaps all as strings.
